<details>
<summary><strong>↳ Follow-up: Explain what Helm charts are.</strong></summary>

**Answer:**
A **Helm Chart** is a packaged collection of pre-configured Kubernetes YAML templates and configuration files. It acts as the package manager for Kubernetes (similar to `apt` or `yum` for Linux, or `npm` for Node.js).

### Key Components of a Helm Chart:
```text
my-app/
├── Chart.yaml          # Metadata about the chart (name, version, appVersion)
├── values.yaml         # Default configuration values for templates
├── charts/             # Dependency charts (subcharts)
└── templates/          # Kubernetes resource manifest templates
    ├── deployment.yaml
    ├── service.yaml
    ├── ingress.yaml
    ├── hpa.yaml
    └── _helpers.tpl    # Reusable template helper definitions
```

### Why We Use Helm Charts:
1. **Parameterization:** Replaces hardcoded values in YAML with Go template variables (e.g., `{{ .Values.replicaCount }}`).
2. **Reusability Across Environments:** The same manifest templates can be deployed to Dev, Staging, or Prod simply by passing different `values.yaml` files.
3. **Release Management & Rollback:** Helm tracks release revisions, making it easy to upgrade or rollback with a single command (`helm rollback`).
</details>

<details>
<summary><strong>↳ Follow-up: Can you explain how Helm charts work with a concrete example, such as passing values to a chart during installation?</strong></summary>

**Answer:**
Helm works by taking a parameterized **template file** and injecting values from a **values file** or CLI arguments to generate standard Kubernetes manifests.

### Concrete Example:

**1. Template (`templates/deployment.yaml`):**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-app
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: web
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          ports:
            - containerPort: {{ .Values.service.port }}
```

**2. Default Values (`values.yaml`):**
```yaml
replicaCount: 1
image:
  repository: myrepo/app
  tag: "1.0.0"
service:
  port: 8080
```

**3. Environment Override (`values-prod.yaml`):**
```yaml
replicaCount: 5
image:
  tag: "1.2.0"
```

**4. Installation Methods:**
- **Method 1: Passing a Values File:**
  ```bash
  helm install prod-release ./my-app -f values-prod.yaml -n production
  ```
- **Method 2: Overriding individual parameters via `--set`:**
  ```bash
  helm install prod-release ./my-app --set replicaCount=3 --set image.tag="v2.1"
  ```
During execution, Helm merges the default `values.yaml` with the override flags/files, renders the manifest with 5 replicas and tag `1.2.0`, and applies it to the cluster.
</details>

<details>
<summary><strong>↳ Follow-up: Explain what the Horizontal Pod Autoscaler (HPA) is and how it works in Kubernetes.</strong></summary>

**Answer:**
### How HPA Works:
HPA operates as a continuous control loop managed by the Kubernetes Controller Manager:

1. **Metric Collection:** Every period (default 15 seconds), HPA queries the **Metrics Server** (or Prometheus Adapter for custom metrics) to get current utilization metrics for the pods.
2. **Target Calculation:** It compares current metric values against the target threshold defined in the HPA manifest using the formula:
   $$\text{Desired Replicas} = \left\lceil \text{Current Replicas} \times \left( \frac{\text{Current Metric Value}}{\text{Target Metric Value}} \right) \right\rceil$$
3. **Scaling Action:** If current utilization exceeds the target, HPA increases the replica count up to the configured `maxReplicas`. When utilization drops, it gradually scales down to `minReplicas` (with a default stabilization window to avoid flapping).

### Prerequisite:
Pods **must have `resources.requests` defined** in their container specification. Without resource requests, HPA cannot calculate the utilization percentage and will report `<unknown>`.

### Example HPA Manifest:
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```
</details>

<summary><strong>● What is AWS DynamoDB, and when should and should you not use it?</strong></summary>

**Answer:**
**Amazon DynamoDB** is a fully managed, serverless, NoSQL key-value and document database service provided by AWS that delivers single-digit millisecond performance at any scale.

### When to Use DynamoDB:
- **Known Access Patterns:** Workloads where query patterns are key-value based (querying by partition key and sort key).
- **High Throughput & Low Latency:** Applications requiring sub-10ms response times at high scale (e.g., e-commerce shopping carts, user session stores, real-time gaming leaderboards, IoT telemetry).
- **Serverless Architectures:** Event-driven apps using AWS Lambda where you want zero server management, automatic scaling, and pay-per-request pricing.

### When NOT to Use DynamoDB:
- **Complex Relational Queries:** When applications require table joins, complex multi-table aggregations, or arbitrary SQL queries (use Amazon RDS or Aurora instead).
- **Ad-hoc / Unknown Query Patterns:** When query requirements change frequently without predefined indexes.
- **Large Blob Storage:** Storing large files or media objects over 400 KB (the maximum DynamoDB item size is 400 KB; use Amazon S3 instead).
- **OLAP / Heavy Analytics:** Data warehousing or analytical reporting (use Amazon Redshift or Snowflake instead).
</details>

<details>
<summary><strong>↳ Follow-up: Setting aside Terraform state locking, in what use cases should you use DynamoDB and in what use cases should you not use it?</strong></summary>

**Answer:**
### Practical Production Use Cases:

**1. Good Use Cases for DynamoDB:**
- **User Session & Authentication Token Store:** Storing user logins, JWT session IDs, or refresh tokens where lookup is strictly by `UserId` or `TokenId`.
- **E-Commerce Shopping Cart:** Fast updates, highly concurrent writes, and automatic item cleanup using **DynamoDB TTL (Time to Live)** to expire abandoned carts.
- **IoT Event & Device Metadata Storage:** Ingesting millions of sensor state records partitioned by `DeviceId` and sorted by `Timestamp`.
- **Feature Flags & Application Configs:** Fast key-value lookups with in-memory caching via DynamoDB Accelerator (DAX).

**2. Scenarios Where DynamoDB is a Bad Fit:**
- **Financial / Banking Systems with Complex Transactions:** Systems requiring strict ACID relational joins across customers, branches, accounts, and audits.
- **Reporting & Business Intelligence Dashboards:** Running `SELECT ... GROUP BY ... ORDER BY` across multiple attributes requires full table scans in DynamoDB, which is slow and extremely expensive.
- **Relational Data with Rapidly Evolving Filters:** Use Amazon Aurora / PostgreSQL instead.
</details>

**Answer:**
### Prometheus:
- **What it is:** An open-source systems monitoring and alerting toolkit designed for dynamic environments like Kubernetes.
- **Core Mechanism:** It uses a **pull-based model** (scraping HTTP metrics endpoints like `/metrics` at periodic intervals), stores data in a **time-series database (TSDB)**, and evaluates alert rules using its query language, **PromQL**.

### Grafana:
- **What it is:** An open-source analytics and visualization web platform.
- **Core Mechanism:** Grafana does not store metrics itself; instead, it connects to data sources (Prometheus, CloudWatch, Elasticsearch, MySQL) to query data and render charts, heatmaps, tables, and dashboards.

### In Short:
**Prometheus is the engine that collects, stores, and evaluates metrics**, while **Grafana is the presentation dashboard that visualizes those metrics** for engineers.

<summary><strong>● If two employees each upload a file with the same name to the same S3 bucket, how can S3 ensure that each user can retrieve and access only their own file?</strong></summary>

**Answer:**
There are two primary industry-standard approaches to solve this in AWS S3:

### Method 1: Prefix / Folder Isolation with IAM Policies (Recommended)
Organize the bucket structure by employee ID or username:
```text
my-company-bucket/
├── user-101/report.pdf
└── user-102/report.pdf
```
Enforce this using an IAM Policy using the AWS policy variable `${aws:username}`:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::my-company-bucket/${aws:username}/*"
    }
  ]
}
```
This guarantees user 101 can only see and retrieve objects inside their own folder.

### Method 2: S3 Object Versioning (If using the exact same path)
- If both upload to `s3://my-bucket/report.pdf`, enabling **S3 Versioning** prevents the first file from being overwritten. S3 assigns unique `VersionId` strings to each upload.
- However, to distinguish ownership, object tagging or custom metadata (`x-amz-meta-uploader: user-101`) must be attached on upload, and the retrieval application queries by version and metadata.
</details>

<details>
<summary><strong>● What is the difference between AWS Auto Scaling and load balancers?</strong></summary>

**Answer:**
While both work together to build scalable, fault-tolerant architectures, they have fundamentally different roles:

| Feature | AWS Auto Scaling (ASG) | Elastic Load Balancer (ELB / ALB) |
| :--- | :--- | :--- |
| **Primary Role** | Manages the **number** of compute instances (scale in / scale out). | Distributes incoming network traffic **across** active instances. |
| **Trigger** | Metric thresholds (e.g., average CPU > 70%, request count). | Operates in real-time on every incoming client request. |
| **Health Check Action** | Replaces / terminates unhealthy instances with fresh ones. | Stops routing traffic to unhealthy targets without terminating them. |
| **Layer** | Management layer (Compute provisioning). | Networking layer (OSI Layer 4 / Layer 7). |

### Analogy:
The **Load Balancer** is like a receptionist directing incoming visitors to available service counters. **Auto Scaling** is the manager who opens new service counters when the waiting line gets too long and closes them when traffic subsides.
</details>

<details>
<summary><strong>● If an application is returning a 503 error, how would you troubleshoot and resolve the issue?</strong></summary>

**Answer:**
A **503 Service Unavailable** error indicates that the server or load balancer is currently unable to handle the request.

### Step-by-Step Troubleshooting Procedure:

#### 1. Check Load Balancer Target Health:
- Inspect the ALB Target Group health status in AWS Console or via AWS CLI:
  ```bash
  aws elbv2 describe-target-health --target-group-arn <tg-arn>
  ```
- If all targets are `Unhealthy`, the ALB returns an immediate 503 because there are zero healthy backends to receive traffic.

#### 2. Check Backend Application / Pod Health:
- In Kubernetes, check pod status and logs:
  ```bash
  kubectl get pods -n <namespace>
  kubectl logs -l app=<app-name> -n <namespace> --tail=100
  ```
- Look for pod crashes (`CrashLoopBackOff`), out of memory kills (`OOMKilled`), or failing health check endpoints (`/healthz`).

#### 3. Verify Health Check Configuration:
- Check if the target group health check path, port, or timeout matches the application configuration. If the app takes 10 seconds to respond to `/health`, but the timeout is set to 5 seconds, targets will be marked unhealthy.

#### 4. Check Resource Saturation (CPU / Memory / Connection Limits):
- High CPU/memory usage or exhausted database connection pools can cause the application to stop accepting incoming connections, causing the load balancer connection to time out.
- Solution: Scale out replicas or instances, and increase database connection pool limits.
</details>

<summary><strong>● Given 100+ AWS EC2 instances, how would you automate generating an hourly report of the instances that are in the terminated state?</strong></summary>

**Answer:**
We can automate this using a Python script with **Boto3**:

### Python Script (`report_terminated_ec2.py`):
```python
import boto3
import csv
from datetime import datetime

def generate_terminated_ec2_report():
    ec2 = boto3.client('ec2', region_name='us-east-1')
    
    # Filter only terminated instances
    response = ec2.describe_instances(
        Filters=[{'Name': 'instance-state-name', 'Values': ['terminated']}]
    )
    
    filename = f"/var/reports/terminated_ec2_{datetime.utcnow().strftime('%Y%m%d_%H%M%S')}.csv"
    
    with open(filename, mode='w', newline='') as f:
        writer = csv.writer(f)
        writer.writerow(['InstanceId', 'InstanceType', 'LaunchTime', 'StateTransitionReason'])
        
        for reservation in response['Reservations']:
            for inst in reservation['Instances']:
                writer.writerow([
                    inst.get('InstanceId'),
                    inst.get('InstanceType'),
                    str(inst.get('LaunchTime')),
                    inst.get('StateTransitionReason', 'N/A')
                ])
                
    print(f"Report generated: {filename}")

if __name__ == '__main__':
    generate_terminated_ec2_report()
```

<summary><strong>● What is the difference between an environment variable and a shell variable in a Linux shell?</strong></summary>

**Answer:**
The fundamental difference is **scope and inheritance to child processes**:

| Feature | Shell Variable (Local Variable) | Environment Variable (Global Variable) |
| :--- | :--- | :--- |
| **Scope** | Available only within the current shell session. | Inherited by any child process or subshell spawned from the current shell. |
| **Creation** | `VAR="value"` | `export VAR="value"` or `declare -x VAR="value"` |
| **Visibility** | Seen by `set`, not seen by `env` or `printenv`. | Seen by both `env` and `printenv`. |
| **Child Processes** | Scripts or subprocesses executed cannot see it. | Subprocesses and commands inherit and read it. |

### Concrete Demonstration:

```bash
# Shell Variable:
MY_LOCAL="hello"
python3 -c "import os; print(os.getenv('MY_LOCAL'))"
# Output: None

# Environment Variable:
export MY_ENV="world"
python3 -c "import os; print(os.getenv('MY_ENV'))"
# Output: world
```

3. **Test Ingress Controller Directly:**

<details>
<summary><strong>● During a production hotfix deployment using Kubernetes rolling updates, a new pod takes about 2 minutes to become ready, and users receive failed responses during that time because the old pod has already been terminated. How can you handle this scenario to avoid downtime?</strong></summary>

**Answer:**
This downtime occurs because the Deployment does not know the application requires 2 minutes to initialize, so it prematurely terminates old pods and routes traffic to the new pod before it is actually ready.

### How to Resolve and Eliminate Downtime:
1. **Configure a `readinessProbe` with Initial Delay / Thresholds:**
   Define a readiness probe pointing to an application health check endpoint. Kubernetes will **not** route traffic to the new pod and will **not** terminate old pods until the readiness probe returns HTTP 200.
2. **Use a `startupProbe` for Slow-Starting Containers:**
   Configure a `startupProbe` with `failureThreshold: 30` and `periodSeconds: 5` (allowing up to 150 seconds for startup). During this time, liveness and readiness checks are disabled.
3. **Configure RollingUpdate Deployment Strategy:**
   ```yaml
   strategy:
     type: RollingUpdate
     rollingUpdate:
       maxUnavailable: 0
       maxSurge: 1
   ```
   Setting `maxUnavailable: 0` guarantees that Kubernetes will never terminate an existing healthy pod until the new replacement pod has completely started and passed its readiness checks.

<details>
<summary><strong>↳ Follow-up: If Kubernetes forwards traffic to a new pod even before the application in it is actually running properly, what can you use to prevent users from hitting the not-yet-ready pod?</strong></summary>

**Answer:**
You use a **Readiness Probe (`readinessProbe`)**.

### How Readiness Probes Prevent Traffic Forwarding:
1. By default, when a container process starts, Kubernetes marks the pod as `Running` and adds its IP to the Service's `Endpoints` object.
2. When a `readinessProbe` is defined, Kubernetes keeps the pod out of the Service Endpoints list (status `NotReady`).
3. Only after the readiness probe succeeds (e.g., returns HTTP 200 on `/healthz`) does Kubernetes add the pod to the Endpoints list and begin routing incoming user traffic to it.
4. If the probe fails at any time during operation, Kubernetes immediately removes the pod from the Endpoints list without killing the container.
</details>

<details>
<summary><strong>↳ Follow-up: How do you set up a startup probe in Kubernetes, and what criteria does it use to decide that the application is running fine and traffic can be transferred to the new pod?</strong></summary>

**Answer:**
### Manifest Example:
```yaml
spec:
  containers:
  - name: my-app
    image: myrepo/app:1.0
    startupProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 5
      failureThreshold: 30    # 30 * 5s = 150s max startup budget
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      periodSeconds: 5
```

### Criteria Used to Decide Success:
1. **Probe Check Mechanism:** Executes an HTTP GET request (`httpGet`), a TCP socket check (`tcpSocket`), or a container command (`exec`).
2. **Success Criteria:** For HTTP GET, any HTTP status code $\ge 200$ and $< 400$ is considered a success.
3. **Transition to Normal Operation:** Once the startup probe succeeds **just once**, it disables itself completely for the life of the container, and hands over monitoring to the `readinessProbe` and `livenessProbe`.
</details>

   - Automatically scale out the number of pod replicas (e.g., from 3 to 15 pods) when average CPU or memory utilization exceeds 65-70%.
3. **Cluster Autoscaler / Karpenter:**
   - Ensure the underlying Kubernetes nodes automatically scale out if new pods cannot fit on existing worker nodes.
4. **Tune Liveness Probe Timeouts:**
   - Ensure `timeoutSeconds` is sufficient so that temporary CPU load spikes don't trigger false restarts.
</details>

<details>
<summary><strong>↳ Follow-up: If a Horizontal Pod Autoscaler is configured and an existing pod restarts under load but new pods do not come up, what could be the reasons?</strong></summary>

**Answer:**
### Common Reasons Why HPA Fails to Scale:
1. **Metrics Server Not Installed / Failing:** HPA relies on the Kubernetes **Metrics Server**. If the Metrics Server is missing or unhealthy, `kubectl get hpa` will show `<unknown>/70%`, and HPA cannot calculate scaling.
2. **Missing `resources.requests` in Pod Spec:** HPA cannot compute percentage-based targets if `spec.containers[].resources.requests.cpu` is omitted.
3. **Scale Target Max Replicas Reached:** The HPA may already have reached its configured `maxReplicas`.
4. **Sudden Memory OOMKill Before HPA Evaluates:** Memory leaks can crash pods instantly (within seconds). Since HPA evaluation period is every 15 seconds, the pod is killed by the OOM killer before HPA triggers a scale-up.
5. **Cluster Node Resource Exhaustion:** HPA might have created the pod objects, but they are stuck in `Pending` state because the worker nodes are out of CPU/memory.
</details>

<details>
<summary><strong>↳ Follow-up: How does Kubernetes obtain CPU and memory usage metrics for the Horizontal Pod Autoscaler to work?</strong></summary>

**Answer:**
Kubernetes gathers resource metrics through the following architecture:

1. **cAdvisor (Container Advisor):** Embedded directly inside the **Kubelet** daemon running on every worker node. It collects resource usage (CPU, memory, filesystem, network) from the Linux kernel cgroups for every running container.
2. **Metrics Server:** A cluster-wide aggregator that regularly polls each node's Kubelet/cAdvisor summary API (`/stats/summary`).
3. **Metrics API (`metrics.k8s.io`):** Metrics Server exposes these aggregated metrics through the Kubernetes API aggregator.
4. **HPA Controller:** The Horizontal Pod Autoscaler queries `metrics.k8s.io` every 15 seconds to evaluate replica targets against current usage.
</details>

<details>
<summary><strong>↳ Follow-up: If a new pod is stuck in the ContainerCreating or pending state and the events show that no node is available, what other reasons could cause this besides affinity or anti-affinity rules?</strong></summary>

**Answer:**
Besides node affinity/anti-affinity rules, other common causes include:

1. **Node Resource Starvation (Insufficient CPU / Memory):** Total `requests.cpu` or `requests.memory` of all scheduled pods plus the new pod exceeds the allocatable capacity of all active worker nodes.
2. **Node Taints and Tolerations:** Worker nodes have taints (e.g., `dedicated=processing:NoSchedule` or `node.kubernetes.io/unreachable`) and the new pod lacks matching `tolerations`.
3. **PersistentVolume (PV) Zone Mismatch:** The pod requires an EBS PersistentVolume located in Availability Zone `us-east-1a`, but all available nodes are in `us-east-1b`.
4. **Exceeded Max Pods per Node / IP Exhaustion:** The AWS VPC CNI on worker nodes has exhausted secondary IP addresses on the node's ENIs, preventing new pods from receiving an IP.
5. **ConfigMap or Secret Missing:** The pod references a ConfigMap or Secret in `envFrom` or `volumeMounts` that does not exist or has a typo in its name.
</details>

<details>
<summary><strong>↳ Follow-up: If the existing nodes lack the resources to schedule new pods, how would you handle this scenario so that new nodes are added and pods get scheduled?</strong></summary>

**Answer:**
To automatically add new nodes when cluster resources are exhausted:

### Solution: Configure Automated Node Autoscaling
1. **Implement Karpenter (Modern AWS Standard):**
   - Install **Karpenter** in the EKS cluster. Karpenter observes unschedulable pods directly and provisions right-sized EC2 instances in under 45 seconds, perfectly matching the pod's resource requests.
2. **Kubernetes Cluster Autoscaler (Traditional Method):**
   - Deploy the **Cluster Autoscaler** pod linked to the AWS Auto Scaling Group (ASG).
   - When pods enter `Pending` state due to `0/N nodes available: insufficient memory`, Cluster Autoscaler automatically increments the ASG `desired_capacity`, launching fresh EC2 instances.
3. **Overprovisioning / Pause Pods (Buffer Strategy):**
   - Deploy low-priority "pause" pods using Kubernetes PriorityClasses to hold node buffer space that can be evicted instantly by production pods without waiting for new nodes to boot.
</details>

<details>
<summary><strong>● In a blue-green setup using two namespaces in the same Kubernetes cluster, the green environment is brought up only during releases. When it is brought up, the application pod is stuck in ContainerCreating and the events say no PersistentVolume is available, even though the PV and PVC exist with the correct name in the same namespace. What could be the reason, and how would you resolve it?</strong></summary>

**Answer:**
### Primary Root Cause:
AWS EBS volumes (`ReadWriteOnce` access mode) **can only be attached to a single EC2 instance in a single Availability Zone at a time**:
1. **Multi-AZ Mismatch:** The existing EBS PV is locked to a specific Availability Zone (e.g., `us-east-1a`). The new green pod was scheduled on a worker node in a different AZ (e.g., `us-east-1b`), so EBS cannot attach across AZ boundaries.
2. **Volume Still Locked by Blue Pod (`Multi-Attach error`):** If both namespaces point to the same underlying EBS volume ID, AWS EBS denies attachment to the green pod because the blue pod is still holding the volume lease.

### How to Resolve It:
- **Solution 1: Use Amazon EFS (Elastic File System) for Shared Storage:**
  Switch the storage class to **EFS (`ReadWriteMany` - RWX)**. EFS supports simultaneous multi-AZ mounting across multiple namespaces without conflict.
- **Solution 2: Node Affinity for EBS PV:**
  Ensure the green pod has `nodeAffinity` matching the PV's exact Availability Zone (`topology.ebs.csi.aws.com/zone: us-east-1a`).
- **Solution 3: Decouple State from Blue-Green Containers:**
  In cloud-native production, applications in blue-green setups should be stateless, storing data in external managed databases (Amazon RDS / DynamoDB / S3) rather than local EBS block volumes.
</details>

<summary><strong>● If infrastructure is managed by Terraform and someone manually whitelists an IP in the AWS console, causing configuration drift to show up in terraform plan, how would you handle this scenario?</strong></summary>

**Answer:**
When configuration drift occurs due to an out-of-band manual change:

### Step 1: Align on Intent
Determine whether the manual change was a temporary diagnostic action or an authorized permanent change:
- **If Unauthorized / Temporary:**
  Run `terraform apply`. Terraform will revert the manual change and restore the security group back to the desired state defined in Git.
- **If Legitimate & Permanent:**
  Update the Terraform `.tf` source code in Git to add the whitelisted IP CIDR block. Run `terraform plan` to verify zero diff (`Infrastructure up-to-date`), then commit and merge the PR.
</details>

<details>
<summary><strong>↳ Follow-up: What is the purpose of the terraform import command, and why would it be needed to handle drift from a manual change?</strong></summary>

**Answer:**
### Purpose of `terraform import`:
The `terraform import` command brings **existing, unmanaged cloud resources** into the Terraform state file (`terraform.tfstate`) without recreating or deleting them.

### When it is Needed:
- If someone created an entirely **new standalone resource** via the AWS Console (e.g., a brand new Security Group, S3 bucket, or IAM Role), Terraform does not track it.
- To bring it under IaC management:
  1. Write the resource block in `main.tf`: `resource "aws_security_group" "new_sg" {}`.
  2. Run `terraform import aws_security_group.new_sg sg-0123456789abcdef`.
  3. Run `terraform plan` and align attributes until zero diff is achieved.

*(Note: If someone simply modified a rule inside an existing managed Security Group, `terraform import` is not needed; `terraform refresh` automatically detects the drift in attributes).*
</details>

<details>
<summary><strong>● You add a new security group rule to existing Terraform code, and terraform fmt and validate succeed, but the new rule does not appear in the terraform plan output, even though the same code is used by the pipeline. What could be the reason?</strong></summary>

**Answer:**
Common reasons why a validated Terraform change does not show up in `terraform plan`:

1. **Uncommitted / Unpushed Code:** The changes were saved locally but not committed or pushed to the branch evaluated by the CI/CD pipeline runner.
2. **Targeting the Wrong Directory or Workspace:** The pipeline executed `terraform plan` inside a different environment directory (e.g., ran in `environments/dev` while you edited `environments/prod`), or a different Terraform Workspace.
3. **Module Not Re-Initialized (`terraform get` / `terraform init`):** If the rule was added inside a child module, the root module uses the cached module in `.terraform/modules/`. Run `terraform get -update` or `terraform init -upgrade` to pull the module changes.
4. **Conditional Logic (`count = 0` or `false` flag):** The rule or resource contains a condition (e.g., `count = var.enable_rule ? 1 : 0`) and the variable in `.tfvars` evaluates to false.
</details>

<details>
<summary><strong>● What is a module in Terraform?</strong></summary>

**Answer:**
A **module** in Terraform is a container for multiple resources that are used together. In fact, any directory containing a set of `.tf` files is a module.

- **Root Module:** The working directory where you execute `terraform init` and `terraform apply`.
- **Child Module:** A module that is called from another module using a `module` block to encapsulate and reuse infrastructure logic (e.g., a VPC module called across Dev, QA, and Prod).
</details>

<details>
<summary><strong>↳ Follow-up: How do you call a child module from a root module in Terraform?</strong></summary>

**Answer:**
You call a child module using a **`module` block** specifying the `source` path and required input variables:

```hcl
module "vpc" {
  source = "./modules/vpc"    # Local path or remote Git URL

  # Passing Input Variables
  vpc_cidr           = "10.0.0.0/16"
  public_subnet_cidrs = ["10.0.1.0/24", "10.0.2.0/24"]
  environment        = "production"
}
```
</details>

<details>
<summary><strong>↳ Follow-up: How does the parent (root) module call a child module in Terraform and pass values to it, and what happens internally between the parent and child modules?</strong></summary>

**Answer:**
### How Values Pass Between Parent & Child:
1. **Inputs:** The parent module defines argument key-values in the `module` block. The child module declares those expected inputs in its `variables.tf`.
2. **Outputs:** The child module computes resources and exports values using `output` blocks in `outputs.tf`.
3. **Parent Consuming Child Outputs:** The parent accesses the child's outputs using the syntax `module.<module_name>.<output_name>`.

### What Happens Internally:
- During `terraform init`, Terraform copies child modules into the hidden `.terraform/modules/` directory.
- During `terraform plan`, Terraform builds a single unified **Directed Acyclic Graph (DAG)** of all resources across root and child modules, automatically calculating dependencies to determine creation order.
</details>

<summary><strong>● How would you use Terraform to create four EC2 servers where two have identical configurations and two have different configurations?</strong></summary>

**Answer:**
The cleanest and most maintainable way is using **`for_each`** over a map of objects in Terraform:

```hcl
variable "servers" {
  type = map(object({
    instance_type = string
    name          = string
  }))
  default = {
    # Two identical web servers
    "web-01" = { instance_type = "t3.micro", name = "web-prod-01" }
    "web-02" = { instance_type = "t3.micro", name = "web-prod-02" }
    
    # Two differently configured servers
    "app-01" = { instance_type = "t3.small", name = "backend-api" }
    "db-01"  = { instance_type = "m5.large", name = "database-cache" }
  }
}

resource "aws_instance" "server" {
  for_each      = var.servers
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = each.value.instance_type

  tags = {
    Name = each.value.name
  }
}
```
</details>

<details>
<summary><strong>↳ Follow-up: How does the for_each meta-argument work in Terraform when creating multiple resources?</strong></summary>

**Answer:**
The **`for_each`** meta-argument iterates over a map or a set of strings, creating an independent resource instance for each item.

### Key Working Principles:
1. **Map Key Identification:** Each resource is identified in state by its map key rather than an integer index:
   `aws_instance.server["web-01"]` instead of `aws_instance.server[0]`.
2. **`each.key` and `each.value`:** Inside the resource block, you access the current key via `each.key` and attributes via `each.value`.
3. **Safe Additions and Removals:** Unlike `count`, deleting an item from the middle of the collection will **only destroy that specific resource**, without causing Terraform to recreate subsequent resources due to shifting array indices.
</details>

<summary><strong>● If a Terraform state file is accidentally removed, what would you do to recover?</strong></summary>

**Answer:**
If the Terraform state file (`terraform.tfstate`) is lost:

1. **Restore from S3 Bucket Versioning (Immediate Solution):**
   - In production, remote state S3 buckets must have **Object Versioning enabled**.
   - Navigate to the S3 bucket, locate the deleted state file, and delete the latest "Delete Marker" or restore the previous version.
2. **Restore from S3 Cross-Region Replication / Backup:**
   - Restore from the backup bucket or AWS Backup vault.
3. **Rebuild State via `terraform import` (Disaster Recovery Fallback):**
   - If no backup exists, you must inspect the existing AWS infrastructure, re-write the matching resource blocks, and run `terraform import <resource> <id>` for each resource to reconstruct the state file without recreating resources.
</details>

<details>
<summary><strong>↳ Follow-up: Where do you store your Terraform state file in your organization?</strong></summary>

**Answer:**
In our organization, we store Terraform state remotely in an **Amazon S3 bucket** with **DynamoDB state locking** configured via the standard S3 backend:

```hcl
terraform {
  backend "s3" {
    bucket         = "myorg-terraform-state-prod"
    key            = "eks-cluster/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-lock-table"
    encrypt        = true
  }
}
```

### Security & Reliability Safeguards:
- **AES-256 Encryption:** Encrypted at rest using AWS KMS.
- **S3 Bucket Versioning:** Prevents accidental deletion and preserves full audit history.
- **DynamoDB State Locking:** Prevents concurrent `terraform apply` executions from corrupting the state file.
- **Restricted IAM Access:** Strict S3 bucket policies allowing only approved CI/CD pipeline roles to read/write state files.
</details>

<details>
<summary><strong>↳ Follow-up: If the Terraform state file stored in an S3 bucket is accidentally deleted by someone, how would you recover it?</strong></summary>

**Answer:**
### Step-by-Step S3 Versioning Recovery:

1. **Enable "Show Versions" in S3:**
   - In AWS Console, open the state bucket and toggle on **Show versions** (or use AWS CLI).
2. **Locate the Delete Marker:**
   - S3 does not physically destroy versioned objects on deletion; it places a **Delete Marker** as the current version.
3. **Delete the Delete Marker:**
   - Execute AWS CLI command:
     ```bash
     aws s3api delete-object --bucket myorg-terraform-state-prod        --key eks-cluster/terraform.tfstate        --version-id <DeleteMarkerVersionId>
     ```
   - Removing the delete marker immediately restores the previous valid state file as the active version.
4. **Verify Recovery:**
   - Run `terraform plan` locally or in the pipeline. It will connect to the restored state and display the correct current infrastructure without attempting to recreate existing resources.
</details>
